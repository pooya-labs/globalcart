# Demo cart, checkout and order design

**Status:** Schema and internal transactional checkout service implemented and CI-verified; no commerce HTTP write API is enabled.
**Scope:** Portfolio simulation only. No real payment, fulfillment, inventory adjustment, customer account or seller payout.

## 1. Ownership and deployment boundary

- A guest cart is identified by a cryptographically random, high-entropy bearer token generated by the server. Persist only its SHA-256 digest in `carts.owner_token_hash`; never log or return the digest.
- The raw token must be delivered only through a secure same-site cookie once a same-site HTTPS frontend/API deployment is approved. Do not expose it in URLs, localStorage, analytics or logs.
- The current GitHub Pages frontend is cross-site from any future API hostname. Therefore no browser cart endpoint or cookie flow is enabled until the owner approves same-site HTTPS hosting, CSRF policy and secret management.
- A future authenticated customer cart can add a nullable user ownership relationship after the identity schema and authorization policy are implemented. Never trust a client-supplied owner/user ID.
- Cart token possession is a capability, not an identity or role. It must not authorize account, seller or admin operations.

## 2. Persistence model

Migration `003_demo_commerce.sql` adds:
- `carts`: token digest, lifecycle status, currency and expiry.
- `cart_items`: product/variant reference, bounded quantity, and display-price/title snapshots.
- `demo_orders`: idempotency-key digest, explicit simulated status, currency and totals.
- `demo_order_items`: immutable product/variant/title/price snapshots independent of later catalog edits.
- `inventory_reservations`: expiring per-order product or variant reservations.
- `demo_order_events`: append-oriented structured event history.

PostgreSQL enforces fixed digest lengths, currency format, valid statuses, positive bounded quantities, nonnegative prices, variant/product ownership, one line per product/variant in a cart, and idempotency uniqueness per cart. Order records are simulation records only; no payment credentials, provider references or addresses are stored.

## 3. Checkout transaction protocol

A future checkout service must perform the complete operation in one PostgreSQL transaction:
1. Validate request size and the cart capability; look up the cart by token digest and lock it with `SELECT ... FOR UPDATE`.
2. Check expiry and lifecycle. For a repeated idempotency key, return the existing order rather than creating a second one.
3. Re-read product/variant active state, price and currency from the database. Never trust client price, title, stock, owner or totals. Cart snapshots are display hints only.
4. Lock the relevant inventory row (`products` when no variant is selected, otherwise the matching `product_variants` row). For a variant, verify it belongs to the product and is active.
5. Calculate available demo quantity as catalog stock minus unexpired active reservations. Reject insufficient quantity; never allow a negative balance.
6. Create the demo order, immutable order-item snapshots, expiring reservation rows and an order-created event; mark the cart checked out.
7. Commit once. On any error, roll back every write.

The row lock serializes competing reservations for the same product/variant. Reservation queries must exclude expired rows even before a cleanup job marks them expired. A cleanup job may transition expired active reservations to `expired`; it must be idempotent.

## 4. Idempotency and state transitions

- Require a high-entropy client-generated idempotency key per checkout attempt; store only its SHA-256 digest and scope uniqueness to the cart.
- Look up the idempotency digest before checking whether the cart is still open, so a network retry can recover the original result.
- Order states: `awaiting_demo_payment` → `paid_simulated`, `cancelled` or `expired`. Terminal states cannot be reopened.
- Reservation states: `active` → `released` or `expired`. A simulated payment result releases the temporary hold; it does not decrement imported catalog stock or trigger fulfillment.
- Append an event for each accepted transition. Event payloads must be schema-validated and must never contain bearer tokens, secrets or payment data.

## 5. Pricing and privacy

- Checkout totals are recalculated server-side from the canonical catalog and variant rows.
- This schema currently keeps subtotal and total equal; taxes, shipping, discounts, coupons and FX conversion are not quoted or implied.
- The current sample catalog is not a promise of real availability. Inventory reservations are demo concurrency exercises, not warehouse commitments.
- No shipping address or other personal data is collected in this schema. A future demo address book requires separate data-minimization and retention review.

## 6. Required tests before write endpoints

- Concurrent checkout requests against one product/variant never reserve more than available demo stock.
- Repeated idempotency keys return the same order and do not duplicate order items, reservations or events.
- Different carts cannot read or mutate each other's cart data by guessing IDs.
- Client-supplied prices, totals, owner IDs and role claims are ignored.
- Expired carts/reservations, invalid variant/product pairs, inactive variants, negative stock and invalid transitions are rejected.
- Rollback removes all partial order, snapshot, reservation and event writes.
- API-level tests verify CSRF, exact Origin checks, request limits, generic errors and authorization before any persistent cart route is exposed.

## 7. Explicit non-goals

No real payment gateway, card/bank data, order fulfillment, shipment, refund, seller payout, customer identity, email delivery or public deployment is implemented or authorized.


## 8. Implemented service boundary
The internal Go service at `backend/internal/commerce/checkout.go` implements the checkout transaction above. It accepts only 32-byte owner/idempotency digests, locks the cart, checks idempotent replay before lifecycle checks, locks catalog stock rows in deterministic cart-item order, reads canonical price/title/stock, subtracts unexpired reservations, and atomically writes order snapshots, reservation rows and an event. It uses PostgreSQL time for cart expiry. It is intentionally not registered with the HTTP router. PostgreSQL integration tests cover stock contention and replay; CI run 41345901209 passed.


The service also provides `ExpirePendingOrders`, an idempotent database operation that marks awaiting-demo-payment orders expired when an active reservation deadline passes, transitions their active reservations to `expired`, and appends a timeout event. It does not alter imported product/variant stock.
