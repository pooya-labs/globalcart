# Demo cart, checkout and order design

**Status:** Schema and internal transactional checkout service implemented and CI-verified; no commerce HTTP write API is enabled.
**Scope:** Portfolio simulation only. No real payment, money refund, fulfillment, inventory adjustment, customer account or seller payout. A full-order return/refund state machine is simulated internally only.

## 1. Ownership and deployment boundary

- A guest cart is identified by a cryptographically random, high-entropy bearer token generated by the server. Persist only its SHA-256 digest in `carts.owner_token_hash`; never log or return the digest.
- The raw token must be delivered only through a secure same-site cookie once a same-site HTTPS frontend/API deployment is approved. Do not expose it in URLs, localStorage, analytics or logs.
- The current GitHub Pages frontend is cross-site from any future API hostname. Therefore no browser cart endpoint or cookie flow is enabled until the owner approves same-site HTTPS hosting, CSRF policy and secret management.
- Migration `012_cart_customer_ownership.sql` adds nullable `carts.owner_user_id`. `BindCartToCustomer` binds a cart only after checking both its capability digest and a live verified customer session; the first account to bind wins. Customer cart/order service methods resolve this owner from PostgreSQL and never accept a client-supplied owner ID.
- Cart token possession is a capability, not an identity or role. It must not authorize account, seller or admin operations.

## 2. Persistence model

Migration `003_demo_commerce.sql` adds:
- `carts`: token digest, lifecycle status, currency and expiry.
- `cart_items`: product/variant reference, bounded quantity, and display-price/title snapshots.
- `demo_orders`: idempotency-key digest, explicit simulated status, currency and totals.
- `demo_order_items`: immutable product/variant/title/price snapshots independent of later catalog edits.
- `inventory_reservations`: expiring per-order product or variant reservations.
- `demo_order_events`: append-oriented structured event history.

PostgreSQL enforces fixed digest lengths, currency format, valid statuses, positive bounded quantities, nonnegative prices, variant/product ownership, one line per product/variant in a cart, and idempotency uniqueness per cart. Order records are simulation records only; no payment credentials, provider references or addresses are stored.

## 3. Checkout transaction protocol

A future checkout service must perform the complete operation in one PostgreSQL transaction:
1. Validate request size and the cart capability; look up the cart by token digest and lock it with `SELECT ... FOR UPDATE`.
2. Check expiry and lifecycle. For a repeated idempotency key, return the existing order rather than creating a second one.
3. Re-read product/variant active state, price and currency from the database. Never trust client price, title, stock, owner or totals. Cart snapshots are display hints only.
4. Lock the relevant inventory row (`products` when no variant is selected, otherwise the matching `product_variants` row). For a variant, verify it belongs to the product and is active.
5. Calculate available demo quantity as catalog stock minus unexpired active reservations. Reject insufficient quantity; never allow a negative balance.
6. Create the demo order, immutable order-item snapshots, expiring reservation rows and an order-created event; mark the cart checked out.
7. Commit once. On any error, roll back every write.

The row lock serializes competing reservations for the same product/variant. Reservation queries must exclude expired rows even before a cleanup job marks them expired. A cleanup job may transition expired active reservations to `expired`; it must be idempotent.

## 4. Idempotency and state transitions

- Require a high-entropy client-generated idempotency key per checkout attempt; store only its SHA-256 digest and scope uniqueness to the cart.
- Look up the idempotency digest before checking whether the cart is still open, so a network retry can recover the original result.
- Order states: `awaiting_demo_payment` → `paid_simulated`, `cancelled` or `expired`. Terminal states cannot be reopened.
- Reservation states: `active` → `released` or `expired`. A simulated payment result releases the temporary hold; it does not decrement imported catalog stock or trigger fulfillment.
- Append an event for each accepted transition. Event payloads must be schema-validated and must never contain bearer tokens, secrets or payment data.

## 5. Pricing and privacy

- Checkout totals are recalculated server-side from the canonical catalog and variant rows.
- This schema currently keeps subtotal and total equal; taxes, shipping, discounts, coupons and FX conversion are not quoted or implied.
- The current sample catalog is not a promise of real availability. Inventory reservations are demo concurrency exercises, not warehouse commitments.
- No shipping address or other personal data is collected in this schema. A future demo address book requires separate data-minimization and retention review.

## 6. Required tests before write endpoints

- Concurrent checkout requests against one product/variant never reserve more than available demo stock.
- Repeated idempotency keys return the same order and do not duplicate order items, reservations or events.
- Different carts cannot read or mutate each other's cart data by guessing IDs.
- Client-supplied prices, totals, owner IDs and role claims are ignored.
- Expired carts/reservations, invalid variant/product pairs, inactive variants, negative stock and invalid transitions are rejected.
- Rollback removes all partial order, snapshot, reservation and event writes.
- API-level tests verify CSRF, exact Origin checks, request limits, generic errors and authorization before any persistent cart route is exposed.

## 7. Explicit non-goals

No real payment gateway, card/bank data, order fulfillment, shipment, money refund, seller payout, customer identity, email delivery or public commerce deployment is implemented or authorized. The internal return/refund state machine is a demo-only simulation and is not exposed over HTTP.


## 8. Implemented service boundary
The internal Go service at `backend/internal/commerce/checkout.go` implements the checkout transaction above. It accepts only 32-byte owner/idempotency digests, locks the cart, checks idempotent replay before lifecycle checks, locks catalog stock rows in deterministic cart-item order, reads canonical price/title/stock, subtracts unexpired reservations, and atomically writes order snapshots, reservation rows and an event. It uses PostgreSQL time for cart expiry. It is intentionally not registered with the HTTP router. PostgreSQL integration tests cover stock contention and replay; CI run 41345901209 passed.


The service also provides `ExpirePendingOrders`, an idempotent database operation that marks awaiting-demo-payment orders expired when an active reservation deadline passes, transitions their active reservations to `expired`, and appends a timeout event. It does not alter imported product/variant stock.


## 9. Implemented guest cart service boundary
The internal Go service in `backend/internal/commerce/cart.go` implements cart creation, line add/increment, quantity setting, line removal and cart retrieval. It accepts only a 32-byte SHA-256 capability digest, locks the cart row for mutations, checks open/unexpired state, and re-reads canonical product/variant price, title and stock from PostgreSQL. Cart quantities are bounded to 1–99 and current catalog stock. The current catalog has no currency column, so this service explicitly supports USD only rather than implying FX support. PostgreSQL integration tests cover lifecycle operations, stock bounds, variant handling and expiry. These methods are not exposed over HTTP.


## 10. Implemented order read and cancellation boundaries
The internal `GetOrder` service scopes order detail reads through a join from the order to its owning cart and the supplied 32-byte capability digest. It returns immutable item snapshots and chronological event history. An unknown order and an order belonging to a different capability intentionally produce the same not-found error.

The internal `CancelOrder` service locks the owned order in a transaction. Only `awaiting_demo_payment` orders may be cancelled; active reservations are transitioned to `released`, the order becomes `cancelled`, and a `demo_order_cancelled` event is appended atomically. Repeated cancellation is idempotent. Paid-simulated and expired orders are not cancellable. PostgreSQL integration tests cover ownership, snapshot integrity, event history, reservation release and repeat cancellation. Neither service is exposed through HTTP.


## 11. Simulated payment state transition
`CompleteDemoPayment` is an internal-only demonstration transition. It requires the cart owner capability, locks the order, accepts only `awaiting_demo_payment` with a still-live reservation, releases active demo reservations, changes the state to `paid_simulated` and appends a `demo_payment_simulated` event in one transaction. Repeated calls after success return the same order without duplicate events. Unknown and wrong-owner IDs return the same not-found error. Cancelled or expired orders cannot be completed. No payment gateway, payment credentials, card data, webhook or actual funds are involved. The method is not exposed through HTTP.


Verification: CI run 41348079983 passed the PostgreSQL integration/race test suite, sqlc generation, formatting, vet, API/importer builds and Docker image build. The payment simulation remains an internal service only.


## 12. Coupon and discount rules
Coupon codes are normalized to uppercase and stored only as SHA-256 digests. Internal coupon definitions support percentage or fixed discounts, start/end timestamps, minimum subtotal, optional maximum discount, optional global usage limit and a per-guest-capability redemption limit. The latter is deliberately not described as a verified per-customer limit: until account identity exists, a guest can create another cart capability.

Applying a code attaches its coupon ID to an open cart; cart reads expose only a boolean applied-state. Checkout re-locks and revalidates the coupon, uses the canonical catalog-price subtotal, checks the minimum and redemption limits, calculates the discount with PostgreSQL NUMERIC arithmetic, records a redemption and snapshots subtotal/discount/final total in the same transaction. A failed validation rolls back the order and reservations. Percentage discounts are capped at the subtotal and optional maximum discount; fixed discounts are likewise capped at subtotal. No coupon administration or cart/checkout HTTP route is enabled.


## 13. Multi-vendor catalog foundation (migration 005)
Migration `005_vendor_foundation.sql` introduces:
- `vendors` with constrained slug, lifecycle status and vendor type; exactly one platform vendor is permitted.
- `vendor_products` as a vendor-specific offer for either a base product or one of its variants. Price, USD currency, stock, SKU and offer status are scoped to the vendor. Partial unique indexes prevent duplicate base/variant offers and duplicate seller SKUs within one vendor.
- `vendor_price_history` and `vendor_inventory_events` as append-only audit records. Future price/stock service methods must write the offer mutation and corresponding audit row in the same transaction; database triggers are intentionally not used because migrations are executed statement-by-statement by the current migration runner.
- Existing catalog products and variants are backfilled as offers owned by the active `GlobalCart Direct` platform vendor. Initial price and opening-stock audit rows are recorded.

Important compatibility boundary: current cart and checkout services still read `products` / `product_variants` stock and price. Migration 005 does not redirect those services to `vendor_products`, does not split orders by vendor, and does not alter the current public read API. This avoids silently changing checkout semantics before a vendor-aware cart line and order-group transaction can be tested end to end. New products imported after this migration do not automatically receive an offer yet; catalog-import integration is a follow-up task.

No seller membership table is created before verified account identity and role authorization exist. No seller API, seller dashboard, payouts, commission, shipment or production service is enabled.


## 14. Internal full-order return and simulated refund
Migration `010_demo_returns.sql` allows one full-order return request per parent order. Only an order in `paid_simulated` may be returned. The request accepts one of four fixed reason codes: `changed_mind`, `damaged_demo`, `not_as_described` or `wrong_item`; arbitrary free text is not stored.

The owner capability is checked through the order's cart. Unknown and wrong-owner requests return the same not-found result. Repeating a request with the same reason is idempotent; attempting another request for the same order is rejected.

An internal-only review step transitions `requested` to `approved` or `rejected`. Approval snapshots the full persisted net order total (including coupon discount) as the simulated refund amount. A rejected request cannot be refunded. A separate owner-scoped completion step moves the parent order, all vendor child orders and the return record to `refunded_simulated` and appends an order event in one transaction. Repeated review decisions and refund completion are idempotent.

The operation does not call a payment provider, accept payment data, move funds, create shipment labels, or alter product/vendor stock or inventory reservations. The internal review function has no authenticated reviewer identity today; it must remain off the HTTP router until identity, deny-by-default RBAC, audit policy and deployment gates are implemented. The current v1 supports one full-order return, not partial/item-level returns.


## 15. Account-backed customer ownership (M04.12)
Migration `012_cart_customer_ownership.sql` adds a nullable foreign key from carts to users. Binding requires possession of the cart's 32-byte SHA-256 capability digest and a currently valid, verified customer session. The cart row is locked; the first account to bind wins, and a different account receives the same not-found result as an unknown capability. Binding may also attach an already checked-out cart so its order history can move under the customer's account.

Internal account-backed methods are implemented in `backend/internal/commerce/customer_ownership.go`:
- `GetCartForCustomer`, `AddItemForCustomer`, `SetItemQuantityForCustomer` and `RemoveItemForCustomer` check the active account/session/customer role, load canonical `owner_user_id` from PostgreSQL and perform the read or mutation while holding the cart row lock. Product/variant price, title and stock are read from the database.
- `GetOrderForCustomer` and `GetVendorOrderForCustomer` derive parent/child order ownership through the order's cart. Foreign and guest-only resources are hidden behind the same not-found result.
- `CancelOrderForCustomer` authorizes against the same canonical cart owner, releases active demo reservations and updates parent/vendor child order states with an appended event in one transaction. Repeated cancellation is idempotent.

Guest capability methods remain separate and continue to authorize only the cart identified by their digest. Binding a cart does not turn a capability into a user identity or role, and these internal account methods do not expose raw tokens. The public HTTP router, cookies, CSRF middleware and hosted backend remain disabled.

PostgreSQL CI tests cover cross-customer/guest-only IDOR denial, account-bound cart mutations, parent and vendor-child order reads, first-writer-wins binding races, expiry, session revocation and cancellation replay. Backend CI [41403135351](https://github.com/pooya16pg-spec/globalcart/actions/runs/41403135351), Security [41403135364](https://github.com/pooya16pg-spec/globalcart/actions/runs/41403135364), and Pages deployment [41403135344](https://github.com/pooya16pg-spec/globalcart/actions/runs/41403135344) passed on implementation head `928c3867e2d8e109e4e6595f9ac0898cf51b25b9`.


## 18. Internal seller offer lifecycle (M06.5)
Seller offer create/edit/archive are internal Go services. A vendor ID is only a selector; the service revalidates the verified account, exact live session, seller role, active vendor and exact membership under row locks in the same transaction. Offers target existing catalog products and start as drafts. Sellers may edit their own SKU, USD price and stock, pause or archive terminally; self-publish to active is unavailable. Migration 015 increments the offer revision on every UPDATE, including system/importer changes. Seller writes require an expected revision and append before/after state, price/inventory history and redacted audit events atomically. No seller HTTP route or dashboard is enabled.


## 19. Internal seller profile and demo analytics (M06.6)
The internal `GetSellerWorkspaceForSeller` service returns the currently authorized vendor's display profile, offer-state/active-stock aggregates and child-order state counts. Paid amounts are filtered strictly to `paid_simulated` and grouped by currency; these are demo metrics, not real revenue. Customer identifiers, email, addresses, order-item details and payment credentials are not returned. Seller profile mutation is limited to `vendors.display_name`, uses the prior `updated_at` as an optimistic revision token, and appends an actor-attributed audit event in the same transaction. Read/write operations revalidate the exact active membership, account and session. This remains an internal service; no route or dashboard is enabled.
